## 2. Tables

Row counts below are the real, live counts as of this phase — all test/throwaway data created during verification was deleted afterward (see SECURITY.md §2.4/§2.5 for what was tested and how cleanup was verified).

| Table | Rows (live) | RLS | Purpose |
|---|---|---|---|
| `profiles` | 2 | ✅ | One row per `auth.users` id. `role` defaults to `patient`; staff roles (`main_admin`/`sub_admin`/`collection_agent`) mirror the original Firebase model. |
| `main_admin_locks` | 1 | ✅ | Permanent record of who has ever been granted `main_admin`. Never written by client code — only by the signup trigger and `sync_owner_admins()`. |
| `tests` | 15 | ✅ | Individual lab tests. Public read (active only); writes are `main_admin` only, logged to `activity_log` automatically. |
| `packages` | 5 | ✅ | Health checkup packages. Same read/write/logging split as `tests`. |
| `package_tests` | 0 (this catalog uses `package_features` — see below) | ✅ | Structured tests-included list for a package, when a package uses the newer per-test schema. |
| `package_features` | 31 | ✅ | Plain-string feature list for a package (the schema all 5 seeded packages actually use, matching the source app). |
| `coupons` | 0 | ✅ | Not publicly readable — see SECURITY.md §3. Empty because the source app has no default coupons (admin-created only). |
| `appointment_slots` | 8 | ✅ | The 8 real time windows from the source app's booking form. Public read (active only); `main_admin` writes. `default_capacity` (12) is a placeholder pending the business's real per-slot numbers. |
| `bookings` | 2 (real) | ✅ | The core booking record — patient snapshot, collection details, pricing (always server-computed), payment, `status` (coarse lifecycle) + `stage` (fine-grained pipeline, the original app's exact TRACKER_FLOW vocabulary), RBAC ownership fields, plus `source`/`creator_role` distinguishing web/admin/whatsapp origin (Phase 5). No insert/update/delete grant to any client role — every write goes through `create_booking()`/`update_booking_stage()`/`admin_update_booking()`/`assign_collection_agent()`. |
| `booking_items` | 2 | ✅ | One row per item in a booking (package or test), snapshotting name+price. Schema supports multiple items per booking; every booking created so far still inserts exactly one. |
| `collection_addresses` | 2 | ✅ | One-way FK to `bookings` (not circular), created only when `collection_type='home'`. |
| `booking_status_history` | 4 | ✅ | Full audit trail of every stage/status change, plus note-only entries for edits/assignments (Phase 5). Customer-facing RPCs only ever select `new_status`+`created_at` from this table — `note`/`changed_by`/`changed_by_name` are never part of a customer-facing return shape. |
| `activity_log` | 3 | ✅ | **New in Phase 5.** General admin action audit trail (staff/catalog/settings/booking-edit/assignment actions) — `booking_status_history` above remains the booking-specific one. Written only by `private.log_activity()` and triggers on `tests`/`packages`/`coupons`/`app_settings` — no client role has an insert/update/delete grant. `main_admin` sees everything; `sub_admin` sees their own actions plus activity on bookings they can view; `collection_agent` sees only their own actions (RLS-enforced; no nav link is shown for this role). |
| `app_settings` | 3 | ✅ | **New in Phase 5.** Key/value config store — `lab_name`, `support_phone`, `support_email`, seeded from values already public in `index-1.html`/the live site footer, not invented. Public read (every value is already public-facing); `main_admin`-only write, logged automatically. `support_phone`/`lab_name` are live-consumed by the public site footer (`assets/js/shared-chrome.js`). |

## 3. Functions

| Function | Type | Purpose |
|---|---|---|
| `handle_new_auth_user()` | Trigger (`auth.users` → `AFTER INSERT`) | Creates the `profiles` row for every new signup (any provider — email/password or Google, the trigger fires on the `auth.users` row regardless of how it was created); grants `main_admin` only to the emails in `owner_emails()`, only once. |
| `owner_emails()` | SQL, `private` schema | Single source of truth for the 3 approved Head Admin emails — both `handle_new_auth_user()` and `sync_owner_admins()` read from this instead of each keeping their own copy. |
| `sync_owner_admins()` | PL/pgSQL, `private` schema | Idempotent catch-up: promotes any *existing* profile matching an owner email that isn't already `main_admin`, and ensures its lock row exists. Safe to re-run any time (e.g., after adding a future owner email) — a no-op for anyone already promoted, never touches a non-owner email. |
| `prevent_self_role_escalation()` | Trigger (`profiles` → `BEFORE UPDATE`) | Blocks a non-`main_admin` from changing their own `role`/`status`/`parent_sub_admin_id`, even though the RLS policy otherwise allows self-updates. |
| `is_main_admin()`, `is_staff()`, `current_user_role()` | SQL, `SECURITY DEFINER` | RLS policy helpers — avoid recursive policy evaluation. Relocated to the `private` schema in migration 0008 — see SECURITY.md §2.1. |
| `set_updated_at()` | Trigger helper | Keeps `updated_at` current on `profiles`/`tests`/`packages`/`coupons`. |
| `validate_coupon(code, amount)` | RPC, `SECURITY DEFINER` | The **only** public surface for coupon checks — returns validity + discount, never the coupons table itself. |
| `can_view_booking(booking_id)` | SQL, `SECURITY DEFINER` | Shared RLS helper for `booking_items`/`collection_addresses`/`booking_status_history` — mirrors `bookings`' own visibility rule exactly, so the child tables can't drift out of sync with it. |
| `generate_booking_code()` | PL/pgSQL | Collision-checked, bounded-retry generator for `MPD-XXXXXX` codes. See BOOKING_IMPLEMENTATION.md §3. |
| `get_slot_availability(date)` | SQL, `SECURITY DEFINER` | Real capacity check — counts actual non-cancelled bookings per slot for a date. Public. |
| `create_booking(...)` | RPC, `SECURITY DEFINER` | The only way a booking is ever created — by a patient, or by staff on a patient's behalf (Phase 5). Requires `auth.uid()` (rejects anon outright, migration 0010). Validates item/availability/coupon, recalculates price server-side, transactional, idempotent. Detects the caller's own role to decide `creator_role`/`user_id`/`parent_sub_admin_id` — never a value the client sends. See BOOKING_IMPLEMENTATION.md §4 and SECURITY.md §2.3. |
| `update_booking_stage(booking_id, stage, note)` | RPC, `SECURITY DEFINER` | The only way a booking's stage changes. Role-scoped: full flexibility for `main_admin`/`sub_admin`, narrow field-relevant stages for `collection_agent` on their own bookings only. Also logs to `activity_log` (Phase 5). |
| `track_booking(code, phone)`, `track_booking_timeline(code, phone)` | RPC, `SECURITY DEFINER` | The only public surface for checking a booking's status — requires both fields to match; returns minimal safe fields only. `track_booking()`'s return shape gained `final_amount`/`address_line` in Phase 5 (needed for the customer WhatsApp confirmation message — still gated by the same phone match, nothing new exposed to a wrong guess). See BOOKING_IMPLEMENTATION.md §5. |
| `assign_collection_agent(booking_id, agent_id)` | RPC, `SECURITY DEFINER` | **New in Phase 5.** The only way a booking's `assigned_collection_agent_id` changes outside of `update_booking_stage()`'s own auto-assign-on-dispatch. `main_admin`/`sub_admin` only; a `sub_admin` can only assign agents on their own team (`private.validate_agent_assignment()`). Logs to both `booking_status_history` and `activity_log`. |
| `admin_update_booking(...)` | RPC, `SECURITY DEFINER` | **New in Phase 5.** The only way staff edit a booking's patient/collection/address/schedule/notes/status/assigned-agent fields. Deliberately has no amount/price parameter at all — historical pricing never changes via this path. Re-validates slot capacity if the date/slot actually changes. `main_admin`/`sub_admin` only (a `sub_admin` must already be able to view the booking). |
| `admin_dashboard_stats()` | RPC, plain `SECURITY INVOKER` (no `security definer`) | **New in Phase 5.** One-call replacement for 8 separate dashboard count queries. Deliberately NOT `security definer` — runs with the caller's own privileges, so Postgres applies that caller's own `bookings` RLS automatically (`main_admin`: everything; `sub_admin`: their scoped rows; `collection_agent`: their own). No role branching duplicated in the function body. |
| `team_workload()` | RPC, plain `SECURITY INVOKER` | **New in Phase 5.** Same RLS-respecting pattern as `admin_dashboard_stats()`, joined against `profiles` for per-collection-agent counts (today/upcoming/completed/active). |
| `private.log_activity(action, entity_type, entity_id, metadata)` | PL/pgSQL, `private` schema, `SECURITY DEFINER` | **New in Phase 5.** The only inserter for `activity_log`. Called from every write RPC above plus the catalog/settings triggers below. |
| `private.log_catalog_change()`, `private.log_coupon_change()`, `private.log_settings_change()` | Trigger functions, `private` schema | **New in Phase 5.** `AFTER INSERT/UPDATE/DELETE` triggers on `tests`/`packages`/`coupons`/`app_settings` — since those tables are written via direct client calls (not RPCs), this is how their changes still reach `activity_log` without duplicating any logic. |
| `private.validate_agent_assignment(agent_id, caller_role, caller_uid)` | PL/pgSQL, `private` schema, `SECURITY DEFINER` | **New in Phase 5.** Shared validation (agent exists, is an active `collection_agent`, and — for a `sub_admin` caller — is on their team) used by both `assign_collection_agent()` and `admin_update_booking()`, so the rule can't drift between the two call sites. |
| `private.protect_locked_main_admins()`, `private.prevent_locked_main_admin_delete()` | Triggers (`profiles` → `BEFORE UPDATE`/`BEFORE DELETE`) | **New in Phase 5.** Absolute protection for any uid in `main_admin_locks`: blocks role/status changes or deletion regardless of caller — closes a real gap where a main_admin could otherwise demote/deactivate the protected Super Admin via a direct table update. Verified live against a disposable locked test account (not the real one) — see SECURITY.md §2.3. |

## 4. Design decisions worth knowing

- **`profiles` consolidates Firebase's `users` + `staff_users`** into one table (`role='patient'` for regular customers) — a deliberate schema improvement, not a 1:1 Firestore copy, per the explicit instruction to design a proper relational schema rather than blindly porting documents.
- **`package_features` stores a snapshot, not a live join to `tests`** — a package's advertised contents never silently change if a linked test is later edited, matching the "historically accurate" requirement for anything a customer was shown at booking/purchase time.
- **No `finance_admin` role exists** — the source app (`index-1.html`) only ever implements `main_admin`/`sub_admin`/`collection_agent`; a 4th role was not invented despite being mentioned as a hypothetical example in the request.
- **`bookings.status` (coarse) + `bookings.stage` (fine-grained) is a deliberate two-column split**, not redundancy — it mirrors the original app's own separation between a booking's payment/lifecycle state and its operational tracker position, just normalized: the original's separate `tracker_states` collection (with a JSON timeline array) is replaced here by `stage` living directly on `bookings` (always exactly 1:1 with a booking, so no reason for a separate table) plus `booking_status_history` as a proper relational audit trail instead of a JSON array column.
- **`bookings`/`booking_items`/`collection_addresses` have no INSERT/UPDATE/DELETE grant for `anon` or `authenticated` at all** — every write goes through a `SECURITY DEFINER` RPC. This isn't a stopgap; it's the actual intended design, since it's the only way to guarantee price/discount/availability are always server-computed.
- **Realtime is enabled on `bookings` and `booking_status_history`** via `supabase_realtime` publication — verified live for a logged-in user's own booking. Not usable by anonymous guests (no table grant), who get a polling fallback instead — see BOOKING_IMPLEMENTATION.md §5.
- **Real pre-existing data, discovered (not created) during the Phase 4 inspection**, kept for operational transparency: two real `profiles` rows already existed from prior genuine usage — `anmolsaini6180@gmail.com` (now `main_admin`, promoted by `sync_owner_admins()` in migration 0009 — see SECURITY.md §2.2) and `sagarmedi001@gmail.com` (unaffected, remains `role='patient'`). Two real, independently-created bookings also already existed: `MPD-U5XZGR` ("Anmol Saini") and `MPD-3RNZWS` ("Sachin Saini"). None of this was fabricated for a test — it was live data found while verifying the bootstrap migration's effect, and is called out explicitly per the project's no-fake-data / honest-reporting rule.
- **Staff-created bookings never own a patient account row** (`user_id = NULL`, `creator_role = 'staff'`) — Admin Add Booking and WhatsApp Booking exist precisely because a phone-in/WhatsApp customer usually has no Supabase account at all. This mirrors the original app's own "guest booking taken over the phone" model rather than inventing a new one.
- **`admin_update_booking()` has no price/amount parameter, deliberately** — Section 27/41's requirement ("a price change must never retroactively affect an existing booking") is enforced by omission: there is no code path, anywhere, that lets a booking's `final_amount` change after creation except a fresh `create_booking()` call. Verified live: changing a test's price from ₹99 to ₹149 left an already-existing booking at ₹99 and a newly-created one at ₹149.
- **The Add Staff Edge Function (`supabase/functions/admin-create-staff`) is the only piece of this project that touches the Supabase Admin API** — every other privileged operation is a Postgres RPC. This was unavoidable: creating a real `auth.users` row requires the service-role key, which must never reach the browser. The function verifies the caller is an active `main_admin` using their own JWT before ever constructing the service-role client, and hard-rejects any request for `role='main_admin'` — Super Admin status is only ever granted by the DB-level bootstrap (migration 0009), never an admin UI form.
- **Two functions (`admin_dashboard_stats()`, `team_workload()`) are intentionally plain `SECURITY INVOKER`**, unlike almost everything else in this schema — the whole point is to inherit the caller's own RLS automatically rather than re-implement role branching inside the function body. This is the one place in the project where *not* using `SECURITY DEFINER` was the correct, deliberate choice.
- **A real gotcha hit twice this phase, worth recording**: adding a new parameter to an existing function via `CREATE OR REPLACE FUNCTION` creates a second *overload* rather than replacing it if the parameter list differs from every existing signature — the old, unfixed version stays fully live and callable until explicitly dropped (migration 0010b). Separately, this Supabase project auto-grants `EXECUTE` on every new function to `anon`/`authenticated`/`service_role` via a project-level `ALTER DEFAULT PRIVILEGES` — an explicit `revoke ... from anon` is required for anything not meant to be public, and `revoke ... from public` does **not** cover it (migrations 0010c/0010d). Both were caught by `get_advisors` and confirmed fixed with a real unauthenticated HTTP call, not just re-reading the SQL.
