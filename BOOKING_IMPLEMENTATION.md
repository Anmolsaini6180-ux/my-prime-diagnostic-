## 2. Bugs found and fixed *during* this phase (not after)

Being transparent about this because "test the whole thing" only means something if failures get reported, not smoothed over:

1. **`create_booking()`: ambiguous `status` column reference.** `RETURNS TABLE(..., status text)` makes `status` an implicit variable inside the function body; an unqualified `status` reference in the slot-capacity query collided with it. Every booking submission failed until this was caught by actually running the flow and reading the real error. Fixed in migration `0007` with a table alias.
2. **`main_admin_locks` created without RLS enabled** (Phase 1, caught immediately via the security advisor, not left for later). Documented in SECURITY.md.
3. **Coupon silently not applied.** The review page's `draft` was captured once as a `const` at page load; applying a coupon updated `sessionStorage` but not that stale in-memory reference, so the UI showed the discount while the submitted booking didn't have it. Fixed by re-reading the draft from storage immediately before submit.
4. **Patient phone number was being put in a URL query string** (`confirmation.html?...&phone=...`) when redirecting after a successful booking — a real privacy issue caught before it shipped, not after. Fixed by passing it through `sessionStorage` instead, with a graceful fallback (asks for phone verification via Track Booking) if that storage entry isn't present — e.g. a bookmarked/shared confirmation link.
5. **Signup trigger wasn't capturing the phone number** the registration form collects (Phase 1 carryover, fixed in migration `0003`, re-verified in this phase).

Each of these was caught by actually exercising the flow in a browser against the live database, not by reading the code back.

## 3. Booking code format

`MPD-` + 6 characters from a 31-symbol alphabet excluding visually ambiguous characters (`0/O`, `1/I/L`) — e.g. `MPD-HPVYZB`. Generated by `generate_booking_code()` with a collision check and bounded retry loop (not "hope for the best"). Deliberately different from the original app's `MPD-<timestamp>` scheme, which was sequential and guessable.

## 4. Secure booking creation — what `create_booking()` actually enforces

Verified with real tests, not just read from the source:

- **Price**: always looked up fresh from `packages`/`tests` by ID — a tampered client-side price is never used. Verified the returned `final_amount` matches the real catalog price minus a real, server-validated discount.
- **Coupon validity**: delegates to `validate_coupon()`; an invalid/expired/limit-reached code raises an exception, aborting the whole booking (no partial state).
- **Slot capacity**: counts real non-cancelled bookings for the date+slot and compares to `appointment_slots.default_capacity`. Verified live: temporarily set a slot's capacity to 1, booked it once (succeeded), attempted a second booking for the same date+slot (rejected with "This time slot is fully booked"), restored the original capacity.
- **Idempotency**: verified two calls with the identical `idempotency_key` produced exactly one database row, not two.
- **Transactionality**: the entire function body is one implicit Postgres transaction — any `raise exception` (invalid item, invalid slot, full capacity, bad coupon) rolls back everything already inserted in that call. No broken partial bookings are possible.

## 5. Public Track Booking — the security decision that was made

[BOOKING_FLOW.md §6.2](BOOKING_FLOW.md) left this as an open decision after Phase 0's audit. It's now decided and built: **Booking Code + the exact phone number used at booking time**, verified server-side inside a `SECURITY DEFINER` RPC (`track_booking` / `track_booking_timeline`) that returns only safe, minimal fields — never internal notes, staff names, or any other booking's data. A wrong phone against a real code returns the same "not found" result as a wrong code entirely, so an attacker can't use the response to learn which half they guessed correctly.

**Realtime honesty**: a logged-in patient viewing their own booking (via My Bookings) gets genuine Supabase Realtime — verified live in this session (a database-side stage change appeared in the browser with zero manual refresh). A guest using the public Track Booking page cannot — `anon` has no table-level grant on `bookings`, which is what makes the phone-verification model secure in the first place. That page instead polls the RPC every 25 seconds and offers a manual refresh button, both clearly labeled as such rather than presented as if they were push-based.

## 6. RBAC on booking actions

`update_booking_stage()` enforces, in the database, not just the UI:
- `main_admin` / `sub_admin`: can set any valid stage on any booking in their scope — matches the original app's admin tracker, which also never enforced a strict linear order.
- `collection_agent`: restricted to `dispatched`, `collected`, `cancelled`, `no_show` (the stages an actual field agent's job covers), and only on bookings assigned to them or created by them. Verified live: an agent attempting a disallowed stage, or a booking not assigned to them, is rejected with a specific error; a patient account attempting to call this RPC at all is rejected outright.

## 7. What's still open

- **`get_advisors` WARN list**: several internal helper functions (`is_main_admin`, `can_view_booking`, etc.) are technically callable directly via RPC by anyone, because Postgres grants `EXECUTE` to `PUBLIC` by default and revoking it would break the RLS policies that depend on calling them. The correct fix (relocating them to a non-PostgREST-exposed schema) is scoped as its own follow-up migration — see SECURITY.md.
- **Guest realtime**: polling, not push, by design (see §5). A future option is a narrow Edge Function or a dedicated `public_tracker` view with its own scoped Realtime channel, if this becomes a priority.
- **Admin UI for stage transitions**: the RPC is done and tested; no admin page calls it yet, per explicit instruction to hold the admin migration for a later phase.
- **Cash/received-amount reconciliation, WhatsApp manual booking, coupon admin UI**: all still live only in `index-1.html`, untouched.
